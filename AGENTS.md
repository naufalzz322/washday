# Laundry shop prototype

## Project overview
A multi-file, mobile-oriented visual prototype for a single-shop wash-and-fold service. The app entry is `prototype/pages/index.html` (Welcome), which leads to sign-in and the customer, clerk and owner areas. There are 27 pages — Welcome plus 26 app screens — all reachable through the app’s own links; there is no separate screen index. Customer tabs are Home, Orders, Vouchers and Profile; Clerk tabs are Home, Queue and New order; Owner tabs are Home, Services, Vouchers and More. Owner More contains Orders, Activity log, Settings and Shop tools. Customer Home is the reference for the compact top app bar and floating icon-plus-label navigation; device status chrome is not simulated, and role-specific tabs retain the same geometry. Below 380 px, all tabs stack the icon above the label so labels stay readable; Clerk and Owner screens use a denser shared card/heading scale. Clerk and Owner Home are dashboards whose figures are deterministic fixtures; the UI presents them as shop figures, and the synthetic boundary is documented here and in `PROJECT_INTAKE.md`, not in the app. Screens remain static/synthetic previews; this is not a complete app or production system. The UI uses natural product copy: no visible demo, sample, preview or “not connected” banners.

## Requirements and phase gates

- App entry: `prototype/pages/index.html` (Welcome); the app is navigated only through its own links. Customer Home uses an order-first layout with a floating New order dock above the bottom navigation, and Orders uses the same dock. New Order is category-first and opens `category-services.html?category=<id>`; it creates no order. The other screens are static visual app screens. Treat the complete set as awaiting review; only add/alter pages in response to feedback.
- Owner catalog: `services-and-prices.html` lists categories and links to `add-category.html`; `owner-category-services.html?category=<id>` lists that category’s services with links to `add-service.html?category=<id>` for adding or editing. Categories and services persist in `sessionStorage` for the current tab; images are compressed locally into data URLs with no upload. `shop-tools.html` restores the catalog and clears recent audit events. Activity log combines earlier history events with this session’s catalog changes and old → new values.
- Shared CSS is in `prototype/assets/css/`; local page scripts are in `prototype/assets/js/`. Generated screens can be refreshed with `python prototype/tools/generate-review-pages.py` (24 generated; Welcome, Customer Home and New Order are hand-built).

## Flutter mobile frontend
- `mobile/` is a Flutter 3.41.1 UI preview for Android and iOS, built from the prototype visual reference; its web target is for local review only. The prototype remains unchanged and is not replaced. The preview has 30 screens in 35 routes: 13 customer, 6 clerk and 14 owner routes plus Welcome and Sign in, with Settings shared by all roles and the staff order detail and weigh screens shared by Clerk and Owner.
- The preview's visual language is a flat Swiss-utility system inside the Welcome identity: Inter Tight, cool off-white canvas and petrol teal, opaque white cards with hairline borders, deep-ink editorial headings, and teal reserved for status and actions. Shadows are limited to the deep dashboards, image overlays and receipt paper. Tokens are in `mobile/lib/app/theme.dart`, shared components in `mobile/lib/shared/ui.dart`.
- Customer tabs are Home, Orders and Vouchers. Profile, Notifications and Loyalty now sit under Settings, reached from the top-bar account menu; that menu shows the signed-in account and also offers Log out for every role. Clerk and Owner share the Settings hub with role-specific preferences, and Owner Settings links to Shop settings. Sign in has no back link and requires an explicit submit: the account picker fills the seeded email and password without navigating, and empty fields, an unknown email or a wrong password show inline errors instead of routing.
- Order lifecycle: Pending → Accepted → Received → Processing → Ready → Picked up; Declined (with a required reason) and Cancelled (customer, Pending only) are terminal. Customer New order → Category services → Checkout → Order placed creates a pending in-memory order, and cancelled orders appear only under All. Clerk and Owner can both accept, decline, record drop-off, weigh with payment, mark ready and mark picked up; Owner uses `/owner/orders/:id` and `/owner/orders/:id/weigh`. Activity events record the acting role. The 16-order seed is re-anchored to the launch day on the UTC+7 shop clock (Customer A 10, Customer B 5, one walk-in; initial requests `LDR-0051`/`LDR-0052`; next order `LDR-0053`). Shop tools was removed from the Flutter preview; the owner catalog still lives in app memory.

- Flutter uses `go_router` for routes and `flutter_riverpod` for session, order and catalog state. Order screens, customer views and dashboard recent orders read the in-memory orders controller; dashboard KPI, chart and service-mix figures are synthetic fixtures. Catalog edits, preference switches and the session reset on restart. Pull-to-refresh is enabled on the primary read screens after sign-in: customer Home, Orders, Vouchers, Notifications, Loyalty, Profile and category services; clerk Home and Queue; owner Home, catalog, vouchers, orders, activity and category services. Forms, order details, receipts and settings stay static. Customer Orders keeps All / Active / Declined / Collected chips and adds a compact Filters button beside them. One Filter orders sheet combines those statuses with Any date / Today / Last 7 days / Last 30 days / Custom range; presets follow the current shop day, while tests fix the clock to 14 Oct 2026. Custom range opens a compact one-month calendar with month arrows and separate Start/End field buttons instead of the full-screen range picker. Tap Start or End to make that field active, then tap a day, so one calendar tap changes only the active field. End is unavailable until Start is set and cannot precede Start, Clear resets both, and Use dates stays disabled until both are set. The calendar spans January of the current shop year through the current month and disables dates after today. An active date filter appears as a removable tag, status and date combine, the count pill shows “3 orders” or the visible “n of 3”, and Clear filters resets both. Pull-to-refresh replays the same session orders for 700 ms; Orders shows its skeleton, other screens the standard spinner. Filtering and refresh fetch and change nothing. The web preview opts into mouse drag so the pull gesture can be reviewed without a touch device. The customer Vouchers page presents WELCOME10 as its primary action with a local Copy control and in-place “Copied” confirmation; it has no Browse services CTA and does not redeem the voucher. Receipts are in-app views over collected orders’ recorded payment. There is no backend, durable order creation, printed receipt, scanning, notification delivery or sync.
- Run checks in `mobile/`: `dart format lib test`, `flutter analyze`, `flutter test`. Run with `flutter run -d <device-id>`; for a local browser preview use `flutter run -d web-server --web-hostname 127.0.0.1 --web-port 8085`. Details are in `mobile/README.md`.
- The Flutter UI is a local-state review preview. Gate D is confirmed for that UI-preview scope only — not for the full five-minute walkthrough, production readiness or owner sign-off. Do not add backend, printer or scanner integration without a confirmed phase decision.

## Commands
- App walkthrough: open `prototype/pages/index.html` to start at Welcome, then use the app’s own links and role navigation. Home and New Order are also directly openable. Everything works from local files without a server/network; catalog changes stay in the current tab’s session storage.
- Run checks from the project root: `node --test tests/*.test.cjs`; syntax-check every local script with `for f in prototype/assets/js/*.js; do node --check "$f" || exit 1; done`; regenerate generated pages with `python prototype/tools/generate-review-pages.py`.
- There is no package manifest, application server, deployment, or backend; tests use Node’s built-in runner.
